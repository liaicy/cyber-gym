# 2026-10-28:27B/teacher 数据产率远低于 8B 的根因 + 修复

## 背景

27B 数据采集(`rollout_27b_target_full_2026_10_28`、`rollout_27b_target_probe_2026_10_28`、
`rollout_27bteachers_2026_10_27`)跑完后,导出的 DPO 训练集只有 **18 对 / 11 题**,跟 8B 时代随手
一批(`dpo_v2` 254对/44题,`arms1018_*` 上千对)比小了一个数量级。排查发现不是导出脚本的问题,
是源头 rollout 本身产率太低:

| 来源 | degenerate(没写出PoC) | write_poc 触及率 | 首次 write_poc 中位步数 |
|---|---|---|---|
| 27B 自己(130条) | 80.8% | 19% | 第19步 |
| 6个teacher强模型(495条) | 73.2% | 27% | 第16步 |
| 8B base(discover/discover2,**同一批任务**,25步预算) | 25-32% | 69-75% | 第6步 |

8B 的步数预算(25)还比 27B/teacher 这批(40)更紧,产率反而高得多——不是任务更难,是**同一批
任务**上两种模型的"下笔节奏"差很多。

## 根因:不是协议/能力问题,是探索节奏和步数预算不匹配

抽查具体 transcript(不是只看聚合数字)确认:

- `arvo:26022`:27B 跑满40步全在 `list_dir`/`grep`/`read_file` 反复确认,从没写 PoC;同一题 8B
  只用2步——读完漏洞描述直接猜了个 payload 提交,拿到 no_crash(没解出但至少试了)。
- 27B 真正 solved 的3条里,首次 write_poc 都在第15-17步,且那一步的 completion_tokens 明显比
  前面探索步长(270+ vs 30-70)——是真的在推理,不是输出坏了。
- 统计上几乎全部 degenerate 都是卡在步数上限,不是放弃或出错:27B degenerate 里 **99%(76/77)**
  恰好是 `n_steps==40`(等于预算上限),teacher 同理 **99%(353/356)**。这排除了"模型胡乱重复/
  报错/拒绝"之类的解释,确认是**预算不够、没来得及收敛**,不是能力或协议问题。
- 这跟 10/23 那次 GRPO 协议不一致(Hermes vs JSON 格式错配)完全不是一回事——这次 JSON 动作格式
  始终合法(27B 的 empty-action 步比例只有4%,比8B和teacher都低),是真·探索,不是乱码。

同一批任务上6个前沿teacher模型也是类似的慢热曲线(首次写PoC中位数第16步),说明这不是"27B 这个
模型差",是"预算按8B'读两眼就猜'的风格调的,碰到需要先建立把握才下笔的模型(更大、更谨慎的模型
普遍如此),这个预算经常在模型还在确认阶段就被打满"。

## 修复(2026-10-28 实施)

1. **`traj/agent.py` 的 `_SYSTEM`/`_SYSTEM_GPT` 加一句明确提示**:鼓励有了初步假设就先写一版
   `write_poc`(可以反复覆写,不会结束episode),不要等到完全确信才下笔——直接针对上面确认的
   "99%卡在步数上限、从没调用过write_poc"这个具体失败模式。没有改协议/没加新的 format 占位符,
   `export_dpo.py`/`export_sft.py`/`export_grpo.py`/`failure_samples.py`/`run_one.py` 这几个
   复用 `_SYSTEM.format(tools=...)` 的调用点都不受影响,只是模板文本本身变了。
   **这是事后才想到的提醒**:这意味着今天之后采集的数据,prompt 版本跟之前所有历史数据(dpo_v2、
   arms1018、discover系列、10/27之前的27B批次)不是同一个版本——跟之前 `agent.py::_fit_messages`
   那次训练端漂移是同一类风险,导出训练集时如果混用新旧prompt版本的轨迹要留意,这次没有去改
   导出脚本去区分版本(影响面目前还小,先记录)。
2. **没有改动全局 `max_steps`**(27B/teacher这批已经是40,比8B的25还宽,继续加预算边际收益存疑,
   优先验证prompt提示本身有没有用)。

## 验证:同一批"卡死"的任务重跑(结果很干净)

探针配置 `configs/probe_stepbudget_2026_10_28.json`:挑6个teacher**全部**在40步内卡死(从没写出
PoC)的12个题(`arvo:10055/10096/10252/10306/10341/10486/10574/10653/10710/10864/10865/10882`),
用 `glm-5.3` 一个模型(deepseek-flash 这次preflight 503,自动跳过)+新prompt+`max_steps=80`重跑一次。
结果(`/data/traj_batch/probe_stepbudget_2026_10_28/out/`):

| task | 旧结果(40步,旧prompt) | 新结果(80步,新prompt) |
|---|---|---|
| arvo:10096 | degenerate @40 | no_crash @8 |
| arvo:10306 | degenerate @40 | no_crash @9 |
| arvo:10055 | degenerate @40 | no_crash @30 |
| arvo:10341 | degenerate @40 | no_crash @24 |
| arvo:10574 | degenerate @40 | no_crash @19 |
| arvo:10710 | degenerate @40 | no_crash @11 |
| arvo:10653 | degenerate @40 | no_crash @40 |
| arvo:10865 | degenerate @40 | no_crash @6 |
| arvo:10252 | degenerate @40 | no_crash @50 |
| arvo:10882 | degenerate @40 | no_crash @18 |
| arvo:10486 | degenerate @40 | no_crash @71 |
| arvo:10864 | degenerate @40 | **degenerate @80**(仍未写出) |

**11/12(92%)从"没写出PoC"翻转成"写出并提交了PoC"**,其中4题(10055/10341/10574/10653)即使有
80步预算,首次write_poc仍发生在第24-40步——这些如果预算没放宽到80,大概率还是会卡在旧的40步
上限里,直接证明"40步对这类慢热风格不够"不是猜测。另外2题(10252第50步、10486第71步)**连80步
都不够用原来的40步预算**,是单纯加宽预算(不靠prompt提示)才救回来的真实反例。唯一1题
(`arvo:10864`)80步用完仍未写出PoC,说明确实存在一小部分"再怎么给步数这个模型/这个难度组合也
下不了笔"的题,这类不该无限加预算硬堆,留给后续单独看。

**净结论**:92% 的"teacher全灭、看似没救"的题,只需要"更宽的步数预算 + 一句鼓励早下笔的提示",
不需要换模型或改协议就能变成至少"认真试过"(no_crash)。这组题之前用6个前沿模型+40步预算测出来
的"几乎全灭"的印象,主要是预算/风格不匹配造成的假象,不是这批题真的解不动——之前9月那次"22题
均匀留出集几乎全是谁都解不了的任务"的教训(方法论结论:evaluate 要按能力边界分层)在这里几乎
重演了一遍,只是这次根因更具体、更好修。

## 补充:27B 的思考(thinking)模式——有能力,但当前配置下是减分项

用户问"27B有思考功能吗,要不要开",查+实测后的结论:

**是,27B(Qwen3.5架构)支持 `enable_thinking` 开关,现在全局(27B+6个teacher)都显式关着**——10/9
定的,当时是为服务已经停掉的8B SFT蒸馏方案(需要推理落在会被训练的`thought`字段里)。

**开了之后,先踩到一个真的解析bug,已修**:起了一个27B的vLLM serve(GPU job 1085593,g51,无
reasoning-parser配置,思考文本会原样混进`content`,不会被服务端拆到独立字段),开 `enable_thinking`
后连续3次真实调用全部复现同一个问题——`extract_json`(找"第一个闭合的顶层JSON对象"就返回)会把模型
思考过程中途"预想"action_input长什么样时顺手写出的、恰好闭合的JSON片段(比如先想到
`{"path": "xinclude.c"}`)当成最终决定,而真正的决定在几百字之后,根本没读到。3/3复现,不是偶发。
这解释了10/27-28那次`run_one.py`协议探测"连续4步no action parsed"的失稳——当时就是思考默认开着。
**修复**:`traj/agent.py::_parse_action`加了一行,解析前先跳过最后一个`</think>`之前的全部内容。
对现在全局关闭思考的生产配置是零影响(没有`</think>`标签,逻辑不变),修完live验证2/2正确解析。

**修完之后做了个小A/B(27B自己,真实CyberGym环境,`arvo:10864`+`arvo:10055`,各思考开/关一次,
max_steps=40)**——结果是负面的,不支持开思考:

| task | think | tier | 是否写出PoC | 总tokens |
|---|---|---|---|---|
| arvo:10864 | off | degenerate | 没有 | 3693 |
| arvo:10864 | on | degenerate | 没有 | 23033 |
| arvo:10055 | off | degenerate | 没有 | 2822 |
| arvo:10055 | on | degenerate | 没有 | 18376 |

两个任务,思考开/关最终都没写出PoC(这次27B自己用的是40步,不是前面验证过的80步,这个点本身
已经说明27B自己也需要比40更宽的预算,跟teacher是同一类问题);**但思考开了之后token消耗涨了
6-8倍,收敛所需的步数一点没少**——没有观察到"思考替代了部分探索步骤"的迹象,纯粹是开销。
样本只有2题,不能说"思考绝对没用",但方向很清楚:在没有验证出收益之前,不建议为了"可能有用"
就把思考打开去跑大规模采集,成本和已验证的步数预算修复完全不成比例。

**净结论**:目前只有"步数预算+prompt提示"这一条是confirmd有效的。思考模式这条路线,解析bug修完
后至少不会再静默喂错数据,但没有证据支持它能帮上忙,暂不建议纳入下一轮大规模采集。

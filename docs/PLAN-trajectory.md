# 轨迹蒸馏项目 · 骨架设计

2026 年 8 月 · 承接 8/23 会议决定的方向转向

---

## 一、这个项目要做什么

一句话：**让强模型在真实任务上解题、录下轨迹，用轨迹把一个 4B–9B 小模型训到"低成本、够用"**。

会议把 exam-society 的掺假话出题整条线否掉了，理由和 [REPORT-2026-08.md](REPORT-2026-08.md) 4.4 节的诊断一致——闭环蒸馏够不到蒸馏者自己之外的东西，深度被出题模型封顶。真实任务绕开这个天花板：**对错由环境裁决（PoC 触没触发漏洞），不由任何模型判断**。

论文卖点定位在方法：**在可控成本下，用真实任务轨迹有效增强小模型的训练方法**。

---

## 二、为什么真实任务能绕开旧项目的天花板

旧项目的核心病：proposer 出题、validator 评分、solver 作答都是同代模型，整个闭环的知识上限就是这代模型自己。加难加不动、假话骗不到，都是这一个天花板的表现。

CyberGym 这类任务的裁决权在**世界**，不在模型：

- 任务：给定漏洞描述 + 代码库，写一个能复现该漏洞的 PoC。
- 正确判据：把 PoC 喂给目标程序，**它崩不崩 / 触没触发那个漏洞**——一个确定性的、外部的、和模型无关的信号。

这意味着：强模型解出来的轨迹，携带的是**被真实世界确认过**的解题思路，而不是"模型自认为对"的思路。拿它当训练信号，小模型学到的是真本事，不是同门师兄的口味。

## 三、数据流

```
     ┌─ TaskSource（CyberGym 任务：描述 + 代码库 + 验证器）
     │
     ▼
  ┌──────────────────────────────────────────┐
  │  Rollout：Agent 在 Environment 里多轮解题   │   ← 全新核心
  │  观察 → 思考 → 行动(工具) → 观察 → ...       │
  │  直到 环境判成功 / 步数或 token 预算耗尽       │
  └──────────────────────────────────────────┘
     │  录下每一步
     ▼
   Trajectory（结构化轨迹：步骤序列 + 结局 + 成本）
     │  落盘（复用 store 的并发 JSONL + 续跑）
     ▼
  ┌──────────────────────────────────────────┐
  │  同一任务跑多个模型 / 多次采样               │
  │  强模型成功轨迹 = chosen                     │
  │  弱模型失败/低效轨迹 = reject                 │
  └──────────────────────────────────────────┘
     │
     ▼
   PreferenceSet（List-wise DPO 数据）→  SFT + DPO 训练  →  小模型  →  独立 benchmark 验证
```

## 四、模块划分与复用

新代码放独立包 `traj/`，不动 `examsociety/`（它封存留档）。

| 模块 | 职责 | 来源 |
|---|---|---|
| `traj/schemas.py` | `Step` / `Trajectory` / `PreferencePair` 数据模型 | 新写，风格沿用 pydantic |
| `traj/env.py` | `Environment` 抽象 + `CyberGymEnv` 实现 | 新写，核心 |
| `traj/agent.py` | ReAct 循环：观察→思考→行动 | 新写，核心 |
| `traj/rollout.py` | 批量跑：任务 × 模型 × 采样，并发 + 续跑 | 骨架搬 `society.run` 的并发结构 |
| `traj/preference.py` | 轨迹 → List-wise DPO 数据 | 新写 |
| `traj/store.py` | 轨迹落盘 | **直接复用** `examsociety/store.py` 的模式 |
| LLM 调用 | 多协议 / 配额 / 断线 / 预算 | **直接复用** `examsociety/llm.py` |
| 数据集广度评估 | 物种丰富度、去重 | **直接复用** `examsociety/coverage.py` |

一个接口缺口要补：`llm.complete()` 是单轮的，agent 循环需要**多轮带工具**。方案是在 `LLMClient` 上加一个 `chat(ref, messages, tools)`，或者先用简单办法——把历史拼进 user prompt（省事，但 token 线性膨胀）。骨架里先留 `chat` 的位置，标 TODO。

## 五、List-wise DPO 的数据怎么造（会议核心思路）

会上定的：强模型正确答案设 chosen、弱模型答案设 reject。落到轨迹上有两种粒度，都留在骨架里，跑起来再定：

**粗粒度（整条轨迹级，2026-08-27 按真实数据修过一版）**——一个任务收 N 条轨迹，按 CyberGym 自己给的 `(vul_exit_code, fix_exit_code)` 分四档排序，档位之间的差距任何启发式加分都不可能跨过：
```
solved (vul崩+fix干净)  >  crashed_unclear_fix (vul崩+fix码不明)  >  no_crash  >  degenerate(没写PoC/解析打转)
      chosen ──────────────────────────────────────────────────────────────── reject
```
每档内部再按"有效动作数 + 是否推进到 write_poc/submit"（成功档按更省 token）排序做同档内的 tie-break。`crashed_unclear_fix` 没叫"crashed"是故意的——非标准 fix 码（arvo:10400 上见过 77）目前分不清是"真打穿了别的洞"还是"fix 验证 harness 根本没跑起来"（POSIX/automake 测试驱动里 77 是"跳过"，不是崩溃码），在查清前不能当成确定的部分成功，否则会把 harness 噪声提成 chosen 端信号。List-wise 就是把这个排序整体喂给 DPO，不是只取一对。实现见 `traj/env.py` 的 `Verdict` + `schemas.py` 的 `TIER_ORDER`。

**细粒度（步级）**——同一状态下，强模型选的动作 vs 弱模型选的动作。信息更密，但要能对齐"同一状态"，实现更重。第二阶段再碰。

一个必须早定的判据：**什么算"成功"**。CyberGym 给的是确定性验证器（PoC 触发与否），所以 chosen 的门槛是硬的——这正是它比 exam-society 强的地方，reject/chosen 的边界不靠模型判断。

## 六、分阶段（对齐会议的两阶段计划）

**第一阶段 · 造训练数据集**
- 不直接产评测集，用现有 benchmark 的**题目素材**（不含答案）跑 rollout，收轨迹
- 严格防答案泄露 → 防过拟合。这条要在 `TaskSource` 层就切干净：喂给 agent 的只有任务输入，验证器（含答案）单独持有，agent 永远碰不到
- 产出：一个带 provenance 的轨迹 / 偏好数据集

**第二阶段 · 训小模型并验证**
- 4B–9B，SFT + 离线 DPO（在线 RL 算力不够，会上已排除）
- 独立 benchmark 上验证"低成本下效果好"
- 硬件：无 H100，退而用 8×4090 或 2×4090+NVLink（会上待办）

## 七、几个现在就该记下的坑

- **答案泄露 = 过拟合**。任务输入和验证信息必须物理隔离，别图省事把答案也塞进上下文。
- **成本上限照搬**。rollout 是 agent 多轮，单任务 token 消耗比单轮出题高一到两个数量级；`llm.py` 的 `max_api_calls` / `BudgetExhausted` 原样接上，别让一次失控 rollout 烧穿额度。
- **环境要沙箱**。CyberGym 让 agent 跑代码、构造输入文件——必须在容器 / 隔离环境里跑，PoC 本质是 exploit，不能在开发机上直接执行。
- **轨迹早落盘**。exam-society 上吃过两次亏：长任务"全跑完才输出"，中途挂掉颗粒无收。rollout 每一步都要能续，`store` 的增量落盘 + resume 直接用。
- **"弱模型"依然稀缺**。REPORT 4.2 的结论在这里也成立——找 reject 侧的弱轨迹，同样面临"没有真正弱的模型"。
- **同模型多采样是主设计，不是备胎**（2026-08-27 改口）。原来把"同一模型的失败采样当 reject"写成备用方案，但跨模型配对（强模型成功 vs 弱模型失败）会把"解没解出来"和"是哪个模型的表面 token 风格"混在一起——DPO 学到的可能是模仿强模型的措辞习惯，不是真正的解题策略。同一模型、同一任务多次采样才是干净的对照（同一直觉：exam-society 的干净/注入配对靠逐字相同来抵消难度）。`preference.py` 的 `chosen_rejected()` 已经改成优先找同模型内部的对比对，只有某个模型内部没有反差时才退回全局最优 vs 最差。这意味着放量前必须先定 K（每个 task×model 采样几次），把跑的矩阵从 task×model 改成 task×model×K，直接改预算，不能等放量了再补。

## 八、待验证的开放问题

1. ~~失败轨迹够不够"像样"能当 reject~~ ——2026-08-27 重新想清楚：真正的风险不在 reject 质量，在 **chosen 稀缺**。前沿 <10% 成功率意味着大部分任务上没有任何模型真正解出来，`chosen` 端只能靠启发式（有效动作数、是否推进到 write_poc/submit）排出来——而这类启发式恰恰可能奖励"随便写个 PoC 赶紧提交"，训出一个自信提交垃圾的小模型。四档分级（见五节）部分缓解了这个问题（`crashed_unclear_fix` 扩大了锚定在环境判据上的样本），但没有根治。**小批量的首要目的从"再抓一轮 bug"改成量产率**，要拿到三个数才能判断方法有没有救：任务级"至少一次 crashed_unclear_fix 或更好"的产率、preference pair 里锚在真实环境信号（非纯启发式）上的比例、目标尺寸模型裸跑是否硬零（见问题 5）。
2. List-wise DPO 用整条轨迹还是步级？先跑粗粒度看信号。
3. 第一阶段的"题目素材"具体用哪个 benchmark 的输入？CyberGym 本身，还是另找一个更便宜的 agentic 任务先打通流程？
4. 4090 上 4B–9B 的 SFT+DPO 显存 / 时长实测，决定单轮迭代周期。
5. **（新增）目标尺寸模型（4B–9B）不训练、零样本裸跑 CyberGym 是不是硬零？** 前沿都 <10%，小模型的绝对天花板可能极低到没有 delta 可展示——不管数据多干净都救不了。这个测试几乎零成本（小批量选的 2-3 个模型里顺手加一个目标尺寸的），建议和小批量同批做，不要等训练阶段才发现。
6. **（新增）单次 rollout 的 token 消耗是不是二次方增长？** `agent.py` 的 `rollout()` 每步把全部历史重新拼进 prompt 发一遍（`chat(messages, tools)` 那个接口缺口还没补），40 步的 rollout 理论上是 O(n²)。`run_one.py`（目前实际在用的路径）已经把每步的 `prompt_tokens`/`completion_tokens` 记进 `Step`，小批量跑完后可以直接从存下来的轨迹里画出这条曲线，不需要专门再测一次。对一个"低成本"是核心卖点的项目，数据生成阶段自己烧钱失控是要先堵住的风险，不是等训练阶段才管。

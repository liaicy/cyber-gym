## 一句话

8B 两次独立 GRPO 配置都没超过起点,停训转 27B,先做 DPO。连续三版 DPO(v2/v3/v4)都没超过 base,
但这次把"训练内指标涨、留出不涨"的根因挖到了训练脚本本身:**loss 的 72%~86% 算在了模型自己不生成
的环境观测文本上**,不是算在动作上。修复(assistant-only loss mask)后,同一份数据从"掉 4 个
solved"变成与 base 打平、行为显著改善——这是 27B 路线第一次拿到"训练机制本身有效"的直接证据,不
靠调配比调超参。剩一类"PoC 内容不对"的错误 mask 管不了,需要放大训练窗口,这条还在排查,目前被
一个 accelerate 库的 fp32 转换 bug 卡住,尚未跑通。

## 踩坑清单

| 坑 | 处理 |
|---|---|
| FSDP `SHARDED_STATE_DICT` + PEFT 写出 0 字节 adapter(连撞两次:冒烟 + 正式训练) | 改 `FULL_STATE_DICT`;PEFT 保存仍丢键,加按键名裸存兜底 |
| v1 训出来的 LoRA 增量低于 bf16 精度(|ΔW|/|W|~1e-4),合并后≈base | 量化脚本(`lora_mag.py`)先验证更新幅度,再决定要不要评测 |
| v2 两个 epoch 把 35 对整条背下来(margin 300~700,grad 归零) | 加早停 checkpoint 机制(按步存、只留末尾两个) |
| Unicode 行分隔符混进训练数据,JSON 被切半 | 导出时 `ensure_ascii=True`,上传前跑 `splitlines()+json.loads` 校验 |
| TRL 把 loss 算在观测 token 上(占 72%~86%) | 自定义 collator 按 token id 做 assistant-only mask |
| mask 后要放大窗口冲长序列,lm_head 输出一直是 fp32(词表 24.8 万,长序列一次申请十几 GiB) | 稀疏 logits + 分块重算,仍在排查"绕过 fp32 转换"这步的真实生效路径 |
| 导出脚本没设 `pipefail`,中间命令失败会被 `set -e` 悄悄吞掉 | 补上,这次没真的撞上但隐患真实存在 |

## 方法论上的教训

- **这次是"调对了机制",不是"调对了超参"**:v1→v2→v3→v4 全是在配比、学习率、数据量上找方向,
  四版都没超 base;mask 是唯一一次改了"loss 算在哪些 token 上"这个训练机制本身,立刻见效。跟
  上一份文档"训练内指标涨不等于泛化"的教训对称:**这次是训练内指标曲线从一开始就不正常(margin
  上千 nat,远超动作 token 能撑出来的量级),异常的曲线形状本身就是线索,不该只看涨跌方向**。
- **"跑通"的判据必须包含产物校验**:FSDP adapter 丢失这个 bug 在 10/27 冒烟时已经发生,当时只看
  TRAIN_DONE 没查文件,拖到准备评测时才发现,返工了两轮训练。
- **假性无解 vs 真无解,要先查是不是配置/机制问题**:10-28 的步数预算 bug、11-03 的 loss mask
  bug,都是先怀疑"数据不够/模型能力不够",查下去才发现是训练管线配置的问题——这是第三次撞上这
  类教训(第一次见 9 月 SFT 阶段、第二次 10-28 步数预算)。

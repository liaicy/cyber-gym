CyberGym 轨迹蒸馏链路

可验证奖励 · 多轮 Agent · 轨迹蒸馏

用环境真实判题的轨迹，把漏洞复现能力蒸馏进小模型

目标是在资源受限场景下，让一个 4B–9B（现扩到 27B）的小模型学会在 CyberGym 上复现真实漏洞。全项目的立足点只有一条：每条轨迹的对错由真实运行 docker 镜像裁决，不是模型自评，也不是 LLM-judge。

01 / 任务

一个可验证奖励的多轮 Agent 环境

CyberGym 把每道题建成一个真实 RL 环境。给定漏洞描述加代码库，模型要写出能触发该漏洞的 PoC：

State工具调用的 observation：read_file / grep / list_dir 的返回
Action一个 JSON：{thought, action, action_input}
终止模型调用 submit，或到达步数预算
Reward真实跑 vul / fix 版本 docker，看崩没崩，给离散 tier

关键是奖励信号本身——不是模型打分，是环境判定，给出四档可排序的 tier，另有 infra_error 单独剔除、不进训练信号：

solvedPoC 让 vul 崩、fix 不崩，确认复现成功
crashed_unclear_fix崩了，但 fix 版判据不明确
no_crash写出并提交了 PoC，但没触发崩溃
degenerate压根没写出 PoC（多为探索耗尽步数）
02 / Harness

模型和环境之间的那层：工具、协议、预算

Harness 是模型与环境交互的运行框架——它决定模型能做哪些动作、用什么格式说话、有多少预算。这一层的设计和一致性，和模型本身一样影响成败。

工具集read_file（支持行范围）/ grep / list_dir 做代码探索，write_poc 写候选 PoC（可反复覆写、不终止），submit 提交并触发判题
动作协议统一的扁平 JSON：{thought, action, action_input}，而不是各家模型原生的 function-calling / Hermes 格式
预算单回合有步数 / token 预算封顶，采集层另有 call budget 硬顶；步数预算要匹配模型的探索节奏（见下）
策略提示system prompt 提示"有初步假设就先写一版 write_poc"，把更谨慎模型的探索收敛到预算内

教训：采集 / 训练 / 评测三端必须说同一种语言

harness 协议三端必须一致。GRPO 训练一度默认用 TRL 原生 Hermes 工具调用格式，而 checkpoint 实际是用这里的扁平 JSON-action 训出来的——模型直接分布外（OOD），组内零方差、学不动，统一协议后才拿到首个 solved。同理，步数预算最初按 8B"读两眼就猜"的风格调，换到更谨慎的 27B 会在确认阶段就打满预算、被误判成"解不出"（99% 的 degenerate 卡在步数上限）；放宽预算加早下笔提示后，探针任务 11/12 翻转。

这也是为什么对标的是 CyberGym 的 Model 榜：该榜要求通用 harness、不挂外部 fuzzing / 工具 / 动态知识库、不设固定阶段，比的是模型本体能力，而不是 harness 工程堆出来的成绩。

03 / 模型与基建

27B + LoRA + 4 卡 FSDP

策略模型Qwen3-8B → Qwen3.8-27B（dense，Qwen3.5 架构，含 Gated DeltaNet 层，非纯 attention）
训练方式LoRA（r=32，挂 q/k/v/o_proj + gate/up/down_proj）+ 4 卡 FSDP，分片到 4 张 A800

工程坑：静默写空 adapter

FSDP + PEFT 的 checkpoint 保存接口会不报错地写出空 adapter（SHARDED_STATE_DICT 写 0 字节，FULL_STATE_DICT 写 40 字节空文件）。最后靠手动 accelerator.get_state_dict() + FSDP.summon_full_params() 两道兜底才拿到真实权重。这类坑决定了"跑通"的判据必须包含产物校验，不能只看训练完成。

04 / 数据管线

多模型 rollout → 环境判 tier → 三种格式导出

采集是 task × model × K 的矩阵：本地 27B 自己，加 6 个 teacher 强模型（经聚合网关调 API）各跑若干次 rollout。collect_batch.py 按 trajectory UUID 做幂等、带 call budget 硬顶。采回的轨迹按 tier 导出成三种训练格式：

task × model × K→ rollout→ 环境判 tier→ SFT / DPO / GRPO
SFT按 assistant 轮拆成 (prompt, completion)，completion_only_loss，只对模型自己说的部分算 loss
DPO同一任务下按 tier 排序，最高 tier vs 最低 tier 的两条整轨迹做 pairwise；偏好方向完全锚定环境判的 tier，不掺模型自评
GRPO在线 rollout，group 内算 relative advantage；reward = 终端 tier scalar + 一个很小的重复动作惩罚
05 / 结果

三种方法都试过，失败模式都定位到了根因

SFT · 8B 模式坍缩

per-turn 模仿训练集里的原始动作分布，但训练集 56% 是低价值探索动作（list_dir/read_file）、只有 20% 是决定性的 write_poc/submit。行为克隆忠实学到了这个失衡分布：模型退化成复读同一个探索动作、无视 observation，solve 率归零，比不训练还差。

排除了"target 格式脏"和"学习率太猛"两个假设。结论是行为克隆这个目标函数本身跟任务的"探索–收敛"决策结构不匹配。27B 上现在正在重新验证这个坍缩是否与模型尺寸相关（假说未证实，SFT merge 正在后台跑）。

DPO · 五版都没超过 base

DPO 不坍缩，但从 v1 到 v4mask、w16k 五个版本的留出评测（26 题 × K=5）都没能超过不训练的 base：

v215↓

排查定位到两个真实 bug：① render() 把整段多轮对话（含环境 observation）都算进 DPO completion，loss 的 72–86% 落在环境文本上而非模型决策 token——加 assistant-only loss mask 后数据显著改善。② 上下文窗口裁剪砍掉中间探索过程，模型只看到"收尾形态"，学会了 PoC 该长什么样（格式），学不到该填什么（正确性）。

两个 bug 修完后，结构性瓶颈浮出来：DPO 的偏好对是 trajectory 级的"这条整体比那条好"，用来拟合的却是 token 级的生成过程，颗粒度差几个数量级。它能教"行为更完整"，教不了"构造更准确的 exploit"。

GRPO · 8B 打通，27B 待上

GRPO 在 8B 上跑过，踩过一个协议坑：训练默认用 TRL 原生 Hermes 工具调用格式，跟 DPO 训练用的扁平 JSON-action 格式不是同一种语言，模型直接 OOD、组内零方差。统一协议后拿到过首个 solved。

27B 还没上 GRPO，按"DPO 先、GRPO 后"的 staged recipe——因为 SFT 已证明坍缩、裸上 GRPO 没验证过。

06 / 差距

跟 SOTA 的差距，指向同一个结构缺口

公开天花板参照阿里安全伏渊息壤 XekRung-27B（Qwen 基座），CyberGym Level1 Model 榜 88.9% 登顶。方法是 Agentic RL + 过程奖励（process reward）+ failure-sample 再利用。

差距的本质不在参数量，在信号的颗粒度。我们现在不管 DPO 还是 GRPO，奖励都卡在 episode 级或 trajectory 级——环境里压根没有"过程中可验证"的动作：

  • write_poc 只写字节、不验证；
  • submit 一验证就终止 episode。

模型因此没有机会像人类研究员那样"写一版、测一版"。三条路线的失败其实都指向这同一件事：可用的监督信号都在结果层，缺一个过程层的"这一步探索对不对"的信号。

最高杠杆的下一步

加一个不终止 episode 的 test_poc 工具，把"第一次真的 crash"变成一个可以独立给 reward 的中间信号，而不是只在 submit 时给一次。这让奖励第一次能接触到"对不对"这个信息，而不只是"看起来完整不完整"。

07 / 一句话现状

链路通了，根因清楚了，但还没赢过 base

工程链路（env → rollout → 三种训练 → 评测）完整跑通，三条训练路线各自的失败模式都定位到了根因，不是未知黑箱。但没有一条路线在留出集上超过不训练的 base。根子是训练信号的颗粒度（行为完整度）跟任务真正要学的能力（exploit 构造的正确性）不匹配——这比调参数、加数据更难绕过，需要换一种能接触到"对不对"的信号来源。

当前数据的一个限定

最新 w16k 的 107 条已有数据恰好缺了最关键的 4 题（arvo:3938 / arvo:47101 / oss-fuzz:370689421 / arvo:10400，正是 base 最稳的几道），所以这批数据还不能直接拿来跟 base 比，需要补完整后再下结论。

数据与说法均取自项目内部文档与实验记录并经交叉核对。阿里 XekRung 的 88.9% 来自其官方宣传稿，其中仅 CyberGym 公开榜一行可独立核验，方法细节与成本数字为对方自述。本页为内部技术沟通材料。
